## slug
review-bottleneck

## post
AI coding agent 没有消灭瓶颈，只是把瓶颈从键盘挪到了责任上。

最近有一篇 Harvard 工作论文（Chen & Stratton 那组讨论）在圈里流传，研究了约 700 多家软件公司、数亿条工作事件。团队用上 Agent 之后，代码量约 +30%，commits 约 +20%，PR 约 +23%。

但交付的 feature、关掉的工单，没有跟着涨。
同期涨的是另一组数字：merge 前的等待和 review 时间约 +49%，打回修改的请求也明显变多。

这不能说明「AI 没用」。效率确实提上去了，只是全卡在人审这一关。

你以为买到了 10x 工程师，其实买到的是 10x 的待审 diff。
写代码的速度，已经超过了你读代码、为它担责的速度。

以前的瓶颈是打字，现在是理解与担责。
reviewer 的注意力是定量的，diff 却几乎免费。生成越便宜，签字越贵。

所以这周该优化的不是生成速度，是你的签收门槛：

1. 验收标准前置。动手前写清「怎样算做完」，Agent 照着交付，人照着验收，别等 review 时才临时想标准。
2. PR 切小。一个 PR 只做一件事，几百行以上默认拆开。大 diff 最后只会换来一句草率的 LGTM。
3. 设 Agent 自测门槛。测试、lint、类型检查没过，不准进人审队列。机器能判的，别浪费人眼。
4. 人只审风险面：权限、数据迁移、涉及钱的逻辑、公共接口、删除操作。其余交给测试和规则。
5. 双 Agent 互审。一个写，一个专门挑刺，人只看两者的分歧点。
6. PR 描述必须写意图：改了什么、为什么改、风险在哪、怎么回滚。意图说不清的 diff，直接退回。

指标也要换。别再盯代码行数和 PR 数，去看「从开 PR 到安全上线」的时长和返工率。

我的判断：Agent 时代，团队的上限不在于能生成多少代码，而在于你敢签收多少代码。

### 审阅动作（主模块，5–6 条短句可执行动作）
- 验收标准前置：先写「怎样算完成」，再让 Agent 动手

- 双 Agent 互审：一个写一个挑刺，人只看分歧

以前的瓶颈是打字，现在是担责。团队上限取决于你敢签收多少代码。
