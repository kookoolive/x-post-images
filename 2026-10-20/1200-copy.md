## post
一篇论文干了件很多人想做没做的事：同一个 Agent、同一个模型，只拨一个开关——子 Agent 开 vs 关。Codex、Claude Code、Kimi Code，354 个任务，2124 次运行，约 2 万美元 API 费。

结论很反直觉：小修小补，开了反而变差。SWE-bench Verified 上，Claude Code 83% → 59%，Kimi Code 77% → 59%，Codex 71% 不动。Claude Code 单题耗时 17.5 → 27.8 分钟。

账也更贵：token 是串行的 1.41–3.31 倍；15 组对照里 14 组反而更慢。真正赚到的只有最长任务：LoopsBench 上 Claude Code 7.1% → 21.4%（28 题，样本小）。

最值钱的是失败归因。作者人工标了 1062 次并发运行，读起来像后端事故单：33% 共享状态冲突（子 Agent 互相覆盖交付物，数据竞争）；29% 执行治理（没跑完就被掐，没人 join 的线程）；28.5% 编排（fan-out 烧光预算，池耗尽）。

我的判断：子 Agent 不是「多开就更快」的性能开关，是一次并发编程。写多线程你会先想清谁拥有哪块内存、在哪汇合；交给 Agent 却默认它自己会想。模型越敢拆，合并越难。

本周 5 件事：
1. 小 bug、单文件改动默认串行
2. 开并发前写清：哪个子 Agent 拥有哪些文件，谁负责合并
3. fan-out 设上限，给整合留时间
4. 只在三种场景开：可独立拆分、两套方案择优、独立验证
5. 按「每个解决任务的 token」记账，不只看通过率

并发从来不免费。人类工程师花了几十年学这课，Agent 不会自动跳过。
