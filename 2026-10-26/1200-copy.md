## post
别把 Agent 画成组织架构图。

Anthropic Applied AI 最近公开建议：企业里很多「编排器 + 一堆 specialist」该折回主循环——一个模型、一个上下文，用 skills 和按需工具干活。某客户实测，单循环比多 Agent harness 大约快 2 倍。

典型死法是 Conway's law：每个产品能力归一个团队，各建一个 subagent，平台组再盖编排器。结果不是更专业，是上下文来回丢细节、subagent 膨胀没 owner、系统提示变成 Frankenprompt、eval 全是本地高分却没人管端到端、延迟把体验拖垮。

对比下来，带 skills 的单 Agent 经常在质量上赢过「一个提示词包打天下」和多 Agent 编排，还更省、更快。客服场景里十几名 specialist，品牌声音都难统一。推荐形态很朴素：开放工具循环里模型自己写计划、自己改计划；skills / tools 只放短描述，完整内容按需加载。Claude Code 对更强模型把系统提示砍了超过 80%。工具定义过大约 30–50 个，选型质量会掉——按用户意图分组，别一 API 一工具。

不是永远不要多 Agent。单循环被上下文撑到可测变差、要并行且子任务上下文用完可扔、或者单 Agent 选工具困难 / 指令冲突——这三种仍该留子 Agent。其余「每个问题类型一个 Agent」，多半是在抄组织图。

怎么迁：先建共享端到端 eval（哪怕 10 条 golden），一次只折一个——prompt 变 skill，API 变 MCP 工具，对比分数。折叠后曾出现主循环自己答、没问物流 specialist，流程反而破，所以每条生产链路都要有任务，而且要多跑几轮。领域组改持有 skills / tools；系统提示和端到端质量，留给一个小而中心的团队。

10-20 我写过 subagent 的 token 税；今天补一句——膨胀往往来自团队边界，不只来自账单。

本周 5 件事：
1. 建共享端到端 eval，别只看子任务分
2. 一次折一个 subagent，用分数决定去留
3. 工具按意图分组，防系统提示堆过 30–50 个定义
4. 中心小组管 system prompt 与上线门禁
5. 只在并行 / 可丢弃上下文 / 选型冲突时开子 Agent

先测，再折。别先画组织图。
