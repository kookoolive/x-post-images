## post
很多人以为卡的是 context。其实先撞墙的是请求体积。

Claude 窗口还空着一大截，截图、PDF、computer-use 轨迹却先把 32MB 请求顶满——这不是「模型记不住」，是管道太细。

Anthropic 官方（@ClaudeDevs）把 Messages + Token Counting 的单次请求上限从 32MB 提到 128MB，大约 4 倍。作用域是第一方 API；Bedrock 和各云市场仍停在大约 20–32MB。多图场景里，单图分辨率上限也从 2000 提到 3000 像素——前提仍是直连 Anthropic。

别把这条读成「上下文又变大了」。context window 和 request payload 是两本账：前者管能塞多少 token，后者管这一次 HTTP 体能有多大。图像、附件、工具轨迹先占的是字节，不是「对话轮数」。Agent 越重视觉、越长会话，越先撞体积墙。

真正值钱的信号是：干活的管道加粗了。computer-use、长 PDF、二十多张图的会话，以前要拆包、砍分辨率、外置 chunker；现在可以先测一次 128MB 能不能整段吃下。还在云市场上跑的人，别默认自己已经拿到这 4 倍——接口路径不同，天花板不同。

本周 5 件事：
1. computer-use / 多图会话改走 Anthropic 直连 API，别默认 Bedrock
2. 大 PDF 任务去掉无用的 chunker，先测单次 128MB 能不能吃下
3. 监控请求字节数与 token 分开记——payload 满 ≠ 窗口满
4. 多图 prompt 用上 3000px 上限前先压分辨率策略
5. 团队文档写明：云市场接口仍是 20–32MB，别混用假设

窗口是脑子的容量；请求体积是干活的水管。这次加粗的是水管。
