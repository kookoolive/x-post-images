1/7
AWS 昨天把 AWS Emulator 做成正式产品：本机起本地 HTTPS 端口，CLI、SDK 和写代码的 agent 用同一套 AWS API 跟它说话，不用 AWS 账号，也不收额外服务费。源码在 GitHub，CC0 授权。

Matthew Goldberg 写：模拟器全部由自主运行的 agent 写成，「我们团队一行代码都没写，也没审过」。
---
2/7
几个容易漏看的细节。起步时是一个能接住 438 个 AWS API Model、什么都不做的空服务器。保真测试有数万条，先在真 AWS 上跑通再对照模拟器；没实现的接口返回 HTTP 501。密钥 ID 以 EMULATOR 开头，默认只听 127.0.0.1:9297。账本摊在 things-that-do-not-work，修好的进 things-that-now-work。
---
3/7
日常维护拆成三组 agent。一组按公开 API Model 写真实场景测试，先在真 AWS 上验证；一组回放测试，找出分叉并提单；一组一次只修一个单。改动要过一道闸：编译、编码规范、安全复查，以及不能把已对齐的行为改回去。过了才进主干。官方说法是，每天数百个 agent 并行，修掉数千个问题。
---
4/7
这套东西最早是周末实验。Goldberg 受 Anthropic「agent 自主写出 C 编译器」启发，给 Kiro 三步：按 CLI 写测试、对着真 AWS 跑绿、再做能通过同一批测试的内存实现。15 分钟后先交出还能用的 SQS，周末把其余服务也搭出来，周一团队就拿来测软件。交给客户用，靠的是后面那套闸，不只是周末。
---
5/7
我的看法：敢把没人审过的代码交给用户，靠的是测试先在真 AWS 上对齐，合入闸对回归和安全复查不留例外。产品博客写明：不要用模拟器测安全。它不会按真 AWS 的方式评估 IAM 和基于资源的策略，云上会拒绝的请求，这里可能放行。本地适合把调用闭环收短，权限和配额还得回真环境验。
---
6/7
我的建议：
1. agent 测 AWS 调用先走本地模拟器，测试环境不要放真正的云凭证
2. 先看该服务的保真分数和 things-that-do-not-work；返回 501 别当成通过
3. 权限、IAM 和限流必须在真 AWS 上验，模拟器放行不算数
4. 让 agent 写实现，先准备能对照真实系统的测试，合入必须过闸
