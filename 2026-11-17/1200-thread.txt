1/9
Claude Code 团队发了一篇讲校验的文章，作者 Addy Osmani。背景一句话：团队大约 90% 的代码由 Claude 写，也由 Claude 审。人读不完每个 diff，整篇在回答靠什么证据放手让 agent 并行干活。
---
2/9
三类测试值得投入。
E2E：整条用户路径要么通要么不通，最难糊弄。单测能过，功能照样可能坏。
属性测试：用 fast-check、Hypothesis、proptest 生成成千上万个输入，去推翻往返编码、不变量、幂等这类断言。
差分测试：旧系统当标准答案，新旧两边跑同一批输入比结果。
---
3/9
校验就是把改动跑起来。仓库里放一个叫 verify 的 skill，写清怎么起模拟器、怎么跑服务，Claude 提交前先用它冒烟。这个 skill 本身要快、要稳。
内部测试里，单独的评分器对照 rubric 检查，结构化文件生成任务成功率最多高 10 个点。
---
4/9
检查红了才叫人。Claude 跑检查、自己修，三轮还红就停下找人。
可靠性清单 39 条，每条带一个能从 diff 读出来的触发条件、对应检查，和背后的事故或 PR。Claude 只核命中的那几条，通常 3 到 10 条。
---
5/9
审查规则放在改动够不着的地方。Code Review 读的 REVIEW.md 来自基线或默认分支，不读 PR 里那份。审查只对那个 commit 有效，审的时候有人又推了提交，结论作废。
Flaky 测试不许绕：不能跳过、不能加 sleep、不能重试到绿。找不到根因就删掉并写明原因。
---
6/9
新门禁先开观察模式。每个 commit 盖章记录怎么验的，值里包括 none，方便查哪些没验。门禁分 off、observe、enforce 三档；同一会话被拦两次，第三次放行，免得卡死。
审查者也被考核：回滚了多少，合入前被维护者拒了多少。
---
7/9
漏掉的 bug 变规则有门槛：同类问题至少出现在 2 个 PR、能从 diff 看出来，再让 3 个 agent 试着推翻，最后人在 PR 里批准。
另一条路：拿已知事故的 PR 回放 3 个找 bug 的 agent，2 个找到就算可检测；小 diff 也漏了，写进 REVIEW.md。
---
8/9
我的看法：这篇最该照搬的是规则文件放哪。规则和改动在同一个分支上，agent 改代码时能顺手改规则，那绿灯就不说明问题。规则也会越攒越多，他们定期清理。
---
9/9
我的建议：
1. REVIEW.md、CI 配置、门禁脚本从默认分支读
2. 新门禁先 observe，看完误拦再 enforce
3. 写一个 verify skill，让 agent 提交前自己跑起来
4. 每条新规则写明出自哪次事故，定期删
