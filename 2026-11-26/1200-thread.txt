1/9
Anthropic 11 月 23 日推出 Claude Ship，目前是 beta。它由三个 agent 组成：已经正式可用的 Code Review，以及还在 beta 的 PR Steward 和 Claude Approvals。开了并不等于会自动合并。
---
2/9
Code Review 从多角度审 PR，结论分成 Important、Nit、Pre-existing，每个仓库可选 Quick、Standard 或 Deep。PR Steward 处理失败的 CI、合并冲突和审阅意见，产品页写明设计上不批准、不合并；每次推送后会评论改了什么、怎么撤。
---
3/9
Claude Approvals 读仓库里的策略文件，策略允许的常规改动可以批。官方建议先开观察模式，只发判断、不真批；确认和人审接近后，再写进 branch protection。管理员按仓库打开 Code Review 和 PR Steward。Approvals 要在默认分支放上策略文件才会启动，也可以关掉。
---
4/9
常被放在一起讲的是本机命令 /ship。文档写明，/ship 和 /steward 跑在你本机的 Claude Code 会话里，用的是你的 gh 和 git 登录，GitHub 上的操作会显示成你的名字。合不合并取决于你的权限和仓库分支规则。文档里的合并步骤是：PR 就绪后，自己合并。
---
5/9
/ship 可以提交、推送并打开 PR，再做 code review，然后在本机会话里处理失败检查、冲突和评论。云端会话没有这两个命令。bypassPermissions 模式、以及原生 Windows，都不会开始看守。公共仓库里，它不会替你提交还没提交的改动。需要 v2.1.330 或更新。
---
6/9
文档还划了一条边界：本机 /steward 和组织产品里的 PR Steward 不是同一个东西。仓库里如果已经有 PR Steward 在干活，本机看守不会启动。看守会把主干合并进你的分支并跑测试，能向主干合入改动的人，相当于能在你这台机器上跑命令。只建议在你信任合入权限的仓库里开。
---
7/9
数字也要看清分母。Claude Code 团队写：6 月到 9 月，合入的 PR 增加了一倍以上，被回退的比例下降了超过 40%。前提是，Claude 的审查只是更宽流程里的一层，不能直接读成「上了 Ship 就会翻倍」。只用在 Team 和 Enterprise 的 GitHub 仓库；开了零数据保留、HIPAA 或客户自管密钥的组织用不了。
---
8/9
我的看法：把评审、修绿、放行拆开，是这套设计里最清楚的部分。PR Steward 可以把 PR 修绿，但不负责放行；放行交给策略文件，而且建议先走观察模式。本机 /ship 也不是云端那套自动流水线，合不合并还在你这边。如果把 Ship 听成会自动合并，会把边界看错。
---
9/9
我的建议：
1. 引用那组数字时，写上这是 Claude Code 团队、审查只是其中一层
2. Approvals 先走观察模式，再写进 branch protection
3. PR Steward 和本机 /steward 要分开配
4. 看守只开在你信任主干合入权限的仓库
