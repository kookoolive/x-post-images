1/9
Anthropic 11 月 25 日发了工程博客，讲 Messages API 从 Python 迁到 Rust。这条 API 是客户以及 Claude Code、Cowork 访问 Claude 的主入口。从 2024 年初到 2026 年秋天，流量大约增长了 1800 倍。Claude 大约用一周写出核心请求路径的第一版，但他们把验证，而不是生成，写成了瓶颈。
---
2/9
对齐很难，原因很具体。迁移期间 Python 版还在改，对等是个移动靶。Claude 对同一请求的回复本身不确定，两边输出不同不一定是 bug。官方不能阅读客户请求，也就不能轻易看见分歧出在哪。
---
3/9
他们先做了增量改写：用 Rust 解析模型输出，再从 Python 调用。CPU 大约只降 8% 到 10%，每个回复 token 还要在 Python 与 Rust 之间穿三次。收益不抵复杂度，于是改走完整迁移。到 2026 年 5 月，Anthropic 合并的代码里超过 80% 由 Claude 撰写。
---
4/9
现成的大约 700 个集成测试也不够当验准器。测试和 Python 实现绑在一起，还要在进程里 mock 计费和限流。审计移植后的测试时，发现 100 多处被削弱的断言。4 月 Rust 版测试大约过了 98%，生产流量上输入对齐大约只有四分之一。缺口一部分来自测试没覆盖到的生产情形。
---
5/9
他们把还在跑的 Python 版当成验准器，对生产流量做 shadow 对照。模型只跑一次，把同一段输出回放到 Rust，避免把不确定性当成 bug。比较的是模型调用前后每一步，而且要完全一致。为了不读请求正文，他们只记录差异的形状：出现在哪一步、prompt 的哪一段、从第几个字节开始、两边各多长，再按这个指纹归类。
---
6/9
每 10 到 30 分钟有脚本把相同差异归到一起，只有新种类才会叫到协调用的 Claude 智能体，再分给工人智能体。内圈在沙箱里用自写请求复现，本地检查往往不到一秒，不调用模型。过了人工审的修复才进外圈，用生产流量的 shadow 看指纹还在不在。工程师在 Slack 里跟进。有一次智能体想把网页搜索工具说明拷进文件来凑对齐，人把它退了，因为上线前还是得去调那个内部服务。
---
7/9
最终每请求 CPU 大约少 70%，首 token 中位时延大约少 20%。全程没有停服务，也没有冻结功能开发。公众流量于 2026 年 9 月切到 Rust。图注写明：CPU 取一个区域，内存取全部生产，时延取一段 Claude Code 请求，时间窗口也更短。正文没有给出内存下降的百分比，转述里的 80% 不宜直接当官方结论。
---
8/9
我的看法：这篇最有用的不是又一组性能数字，而是他们承认测试通过和生产对齐不是一回事，并且把生产系统本身做成了可自动分派的验准信号。校验器能告诉你两边是不是对齐了，判不了这个修法能不能上线。人还是卡在「这是不是该留的差异」和「这个修复是不是在偷懒」。
---
9/9
我的建议：
1. 引用 70% 和 20% 时，写上图注里的分母：CPU 是一个区域，时延是一段 Claude Code 请求
2. 不要把「测试过了 98%」读成已经和线上一致
3. 不要采用正文没写的「内存降 80%」
4. 不要写成 Claude 独自重写并上线了生产 API；协调、修复和放行中间还有人审
