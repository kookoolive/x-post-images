1/9
微软三名作者 11 月 25 日挂上预印本，问的是：编码 Agent 的补丁比开发者大，是不是就是过度编辑。他们做了 Delta Residue Attribution：回放轨迹，把最终补丁拆成可单独撤回的代码块，逐块撤回后再跑任务测试，看这块到底要不要。样本是 18 个前沿模型在 GitHub Copilot CLI 上已经解出的 7,660 条轨迹：SWE-bench Verified 6,728 条，DeepSWE 932 条。开发者补丁用同一套方法打分。
---
2/9
SWE-bench Verified 上，中位模型改动的行数是开发者补丁的 2.33 倍。只看代码单元，这个比例是 0.86，按任务计的中位数是 1.00。不算测试文件，中位仍是 1.09 倍。行数变多是事实，但把 2.33 倍直接读成「代码改多了」，分母不对。
---
3/9
多出来的编辑，在两条基准上长得不一样。Verified 上，61% 是测试文件，21% 是代码，13% 是文档，5% 是注释或格式。81.5% 的 Agent 补丁会改测试文件。DeepSWE 上结构反了：任务偏功能实现，每个补丁的单元大约是前者的六倍，多出来的编辑里 58% 是代码，测试只占 26%。
---
4/9
看代码本身是否必要，Agent 的平均 NP_code 在 Verified 上是 0.887，同一批实例上开发者是 0.864。18 个模型里，11 个显著少于开发者的多余代码，4 个没有显著差异，3 个显著更多，都是 Gemini 3.8、3.7、3.6 Flash。DeepSWE 上是 0.797 对 0.785，没有模型显著高于开发者基线。平均下来，Agent 补丁里仍有 11% 的代码单元被判为不必要。
---
5/9
这 11% 不能略过。3,987 个不必要代码单元里，行为探测覆盖了 3,559 个，其中 89% 会改行为，比如在邻近输入上抛出或吞掉异常。其余 11% 是不起作用的防护或重复检查。「不必要」的意思是：撤回这块，任务测试照样过。不是维护者一定要删。调试步骤几乎写不出这些残留：3,987 个里只有 154 个来自调试，分布在 55 个补丁；83% 是在写修复时写下的。
---
6/9
Agent 补的测试也不是空的。在通过有效性检查的 271 道 Verified 题上，作者往补丁后的代码里注入了 1,962 个小变异。Agent 新增的测试抓住了 68.1%，高于同文件里原有的回归测试 45.6%，低于任务测试的 77.1%。任务测试没抓住的那些变异里，有 22.7%（102 个）被 Agent 新增或加强的测试抓住，相当于全部变异的 5.2%。
---
7/9
过关之后再清理，三条路效果差很多。在 Agent 自己的测试第一次全绿时停下来，3,031 份里有 2,948 份任务测试仍能过，但 NP_code 只从 0.700 走到 0.710。让模型给最终 diff 的每一块写理由，再丢掉它说不清的：精确率 65.7%，召回只有 35.5%，会弄坏 1.8% 已解出的补丁。用 Agent 自己的测试加上仓库里已有的 PASS_TO_PASS 回归测试做剪枝，召回 67.3%，精确率 46.3%，这是 2,495 份合格补丁上的数，其中 89.1% 剪完仍能过关。
---
8/9
我的看法：2.33 倍说明补丁更大，不能说明代码更脏。Verified 上多出来的主要是测试和文档，代码必要度和开发者相当，11 个模型还略干净一些。该盯的是另外两件事：那 11% 不必要、但 89% 会改行为的代码块；以及 DeepSWE 上多出来的部分已经变成以代码为主，不能拿 Verified 的构成去套。过关率高低也带不出代码净不净，DeepSWE 上两者还是负相关。
---
9/9
我的建议：
1. 引用 2.33 倍时写明：SWE-bench Verified、中位模型、含测试文件
2. 不要把 Verified 上「多半是测试」套到 DeepSWE，那边 58% 是代码
3. 过关率高不代表补丁更干净；清理时记住自己审的召回只有约三分之一，自动剪枝精确率不到一半
4. 这些数来自已解出的 Copilot CLI 轨迹，相对的是任务测试；加强版 oracle 下，Verified 上相对开发者的优势还会翻转
